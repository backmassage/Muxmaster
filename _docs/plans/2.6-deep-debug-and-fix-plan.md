## 2. Architecture and Context Summary

Muxmaster is a Go CLI application and orchestration layer over `ffmpeg` and `ffprobe`. It has no non-standard Go runtime dependencies and targets a single static binary, with ffmpeg/ffprobe and encoder availability checked at startup.

Current major components:

- `cmd`: CLI bootstrap, config validation, path safety, diagnostics, analyze mode, pipeline entry.
- `internal/config`: dependency-free defaults, CLI flags, validation, and normalized config sub-structs.
- `internal/check`: runtime dependency and encoder capability checks; shells out directly for diagnostics and cheap VAAPI probes.
- `internal/probe`: dependency-free ffprobe JSON parsing into typed stream metadata.
- `internal/naming`: dependency-free filename parsing, Jellyfin output paths, collision resolution, and TV year harmonization.
- `internal/planner`: combines config plus probe data into `FilePlan`; owns action selection, quality, filters, audio, subtitles, container options, and retry initial state.
- `internal/ffmpeg`: consumes `FilePlan` and `RetryState` to build and run ffmpeg commands.
- `internal/tune`: new near-leaf package that runs the grain pre-pass and maps the signal to a tune suggestion.
- `internal/pipeline`: sole orchestrator for discovery, auto-tune grouping, per-file processing, retry execution, quality escalation, stats, and analyze mode.
- `internal/logging`, `internal/display`, `internal/term`: terminal/log presentation.

Dependency model:

- Dependencies flow top-down.
- Leaf packages are `config`, `probe`, and `naming`.
- `planner` imports only `config` and `probe`.
- `ffmpeg` imports `config` and `planner`.
- `pipeline` wires everything together and is the only package that imports both planning and execution layers.
- `check` and `tune` are documented exceptions to the "all ffmpeg interaction through internal/ffmpeg" convention because they run diagnostics/pre-analysis rather than application encode commands.

Runtime assumptions:

- Sequential batch processing.
- `ffmpeg` and `ffprobe` are available on `PATH`.
- VAAPI mode needs a working `/dev/dri/renderD*` device.
- VAAPI hardware decode is used when viable, with software decode fallback for HDR tonemap, Hi10p AVC, runtime HW-decode failures, and explicit CPU prefilters.
- Non-interactive `--tune auto` resolves to no prefilter.
- Dolby Vision is never preserved: profile 5 is skipped, other DV profiles are stripped/dropped to the HDR10 base layer.

Testing strategy:

- Strong unit/matrix coverage in `planner` and `probe`.
- Builder/retry tests for ffmpeg argument construction and error-class transitions.
- Focused config/naming/pipeline tests.
- Guarded live tests exist for some ffmpeg/probe behavior, but several 2.6 claims still depend on real media or live VAAPI stacks.

Performance goals:

- One ffprobe JSON call per file.
- VAAPI-first encode path.
- Cheap one-representative-per-series tune pre-pass only for interactive `--tune auto`.
- Sequential operation; parallel workers and persistent state are deferred.

Security assumptions:

- External processes are invoked with `exec.Command`/`CommandContext` and argument slices, not shell interpolation.
- Output directory containment checks reject output inside input.
- The tool processes local files and does not expose a network service.

Deployment assumptions:

- Built with `make build` for version/commit injection.
- `make ci` is the intended quality gate: vet, fmt, docs-naming, build, and tests.
- `golangci-lint` is optional but expected for `make lint` where installed.

Version 2.6 intended direction:

- Playback correctness: DV policy, color tagging, mov_text->srt for MKV, sparse subtitle interleave handling, cover art carry-over.
- Encoder behavior correction: QVBR opt-in only, verified VAAPI B-frame support, compression-level documented as inert on AMD VCN HEVC.
- Quality controls: content-aware tune profiles, per-series auto-tune prompt, quality-priority mode.
- Robustness: higher retry cap and additional retry classes.

### Medium

#### M1. `--tune auto` runs before skip-existing, dry-run, and per-file validation

- Severity: Medium.
- Final status: Fixed.
- Confidence: High.
- Affected files, functions, modules, or tests: `internal/pipeline/runner.go` `Run`, `processFile`; `internal/pipeline/autotune.go` `resolveSeriesTunes`; `internal/pipeline/pipeline_test.go` `TestDryRunPipeline`.
- Description: The batch-level auto-tune pass runs immediately after discovery when stdin is a terminal. Normal file validation, probe rejection, output path resolution, skip-existing, and dry-run short-circuiting happen later inside `processFile`.
- Evidence: `Run` calls `resolveSeriesTunes` before the per-file loop in `internal/pipeline/runner.go:41-47`. `processFile` performs size/probe validation in `internal/pipeline/runner.go:79-116`, skip-existing in `internal/pipeline/runner.go:182-190`, and dry-run handling in `internal/pipeline/runner.go:208-218`.
- Why it matters: A default interactive run can analyze and prompt for files that will later be skipped, including already-existing outputs, too-small/corrupt files, audio-only files, or DV profile 5 skips. Interactive dry-runs can also do real ffmpeg pre-pass work despite not writing outputs.
- Likely root cause: Auto-tune was added as a batch pre-pass before the existing per-file decision pipeline.
- Recommended fix: Build a cheap candidate list before auto-tune, or move auto-tune resolution after enough per-file metadata exists to skip known non-candidates. At minimum, skip auto-tune when `cfg.DryRun` unless the user explicitly asks for tune analysis, and avoid analyzing files whose resolved outputs already exist.
- Suggested tests or validation steps: Add a pipeline test with injectable TTY/detect hooks proving dry-run does not pre-pass unexpectedly, and a skip-existing test proving an already-existing output does not trigger `DetectContent`.
- Fix now or defer: Fix now if `--tune auto` remains the default; otherwise document clearly and defer until after release.

#### M2. Auto-tune representative selection can sample an unrepresentative file

- Severity: Medium.
- Final status: Fixed.
- Confidence: Medium.
- Affected files, functions, modules, or tests: `internal/pipeline/autotune.go` `groupBySeries`, `suggestForRep`; `internal/pipeline/discover.go`.
- Description: The representative file for a series is the first path in sorted discovery order. That can be a special, NCOP/NCED, trailer, short, corrupted episode, low-bitrate preview, or otherwise non-representative sample, yet its selected tune is applied to every episode in the group.
- Evidence: `groupBySeries` stores `rep: path` on the first file seen in `internal/pipeline/autotune.go:68-76`. Discovery intentionally keeps specials/NC folders in `internal/pipeline/discover.go:36-38`.
- Why it matters: A bad representative can apply too much denoise or no denoise to an entire season, which is directly in the quality-critical path.
- Likely root cause: The plan optimized for a cheap one-file pre-pass and did not add representative selection heuristics.
- Recommended fix: Prefer normal TV episodes over specials, prefer longer duration, reject very short samples, and fall back to the next candidate when probe/pre-pass fails. A low-cost option is to probe durations for the group and choose the longest normal episode.
- Suggested tests or validation steps: Add a grouping test where `NCOP` or `Season 00` sorts before `S01E01` and assert the representative is a main episode. Add a failed-representative test that chooses the next viable file.
- Fix now or defer: Fix now for quality safety, or defer with a clear "initial heuristic" caveat.

#### M3. Auto-tune orchestration is under-tested and hard to test because it uses global stdin/stdout and real detection

- Severity: Medium.
- Final status: Fixed.
- Confidence: High.
- Affected files, functions, modules, or tests: `internal/pipeline/runner.go`, `internal/pipeline/autotune.go`, `internal/pipeline/autotune_test.go`, `internal/pipeline/pipeline_test.go`.
- Description: Tests cover pure helpers such as `seriesKey`, `groupBySeries`, `parseTuneChoice`, and `promptSeriesTune`, but not the full handoff from a resolved `seriesTunes` map into `processFile` and `planner.BuildPlan`. The TTY gate, prompt IO, and detection function are hardcoded to `os.Stdin`, `os.Stdout`, and `tune.DetectContent`.
- Evidence: The only `Run` integration test is dry-run with non-TTY defaults in `internal/pipeline/pipeline_test.go:188-256`. The auto-tune lookup and cfg copy are in `internal/pipeline/runner.go:137-155`. `resolveSeriesTunes` reads/writes globals in `internal/pipeline/autotune.go:95-104`.
- Why it matters: A mismatch between grouping keys and per-file lookup, or a future regression in the shallow cfg copy, would not be caught by current tests.
- Likely root cause: The new auto-tune flow landed quickly around global terminal IO rather than injectable seams.
- Recommended fix: Introduce a small auto-tune dependency struct for terminal detection, reader/writer, probe duration, and content detection. Keep production defaults identical. Use it to test TTY/non-TTY behavior and per-file tune application without live stdin.
- Suggested tests or validation steps: Add tests for non-TTY default auto -> no pre-pass; explicit `--tune grain` -> no auto pre-pass; resolved `seriesTunes["tv:show"]=grain` -> ffmpeg args contain `hqdn3d=4:4:9:9`; missing key -> no prefilter.
- Fix now or defer: Fix now; this is a small seam with high regression value.

#### M4. QVBR post-encode size escalation has no focused regression test

- Severity: Medium.
- Final status: Fixed.
- Confidence: High.
- Affected files, functions, modules, or tests: `internal/pipeline/runner.go` `executeWithRetry`; `internal/ffmpeg/builder.go`; tests under `internal/pipeline`.
- Description: The changelog notes a 2.6 fix where QVBR oversize escalation must shrink bitrate target/ceiling as well as bump QP.
